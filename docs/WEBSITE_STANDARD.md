# معيار هندسة وتصميم موقع عيادة الدكتورة فايزة | WEBSITE STANDARD

**الحالة:** معتمد كأساس تصميم وتنفيذ الموقع — 2026-11-05.  
**النطاق:** الموقع الإلكتروني فقط؛ ليس استبدالًا لدليل الهوية أو بيانات العيادة.  
**المرجع الهندسي المستفاد منه:** [UPDATE CARD Architecture](https://github.com/7eaur/update_card/blob/main/docs/ARCHITECTURE.md) و[README](https://github.com/7eaur/update_card/blob/main/README.md). نقتبس المبادئ المناسبة، وليس واجهته أو هويته أو خدماته.

## 1. الهدف وتجربة الزائرة
- موقع عربي RTL، مهيأ للهاتف أولًا، يعرض الثقة المهنية والخدمات ومعلومات الزيارة ويقود إلى اتصال/واتساب مباشر.
- المسار الرئيسي: اكتشاف الخدمة ← الاطلاع على وصفها ومقدمتها الطبية ← التعرف على الدكتورة ← التواصل/الوصول.
- لا ننشئ نظام حسابات أو مواعيد أو سجل مرضى قبل اعتماد حاجة تشغيلية واضحة؛ لا نجمع معلومات صحية حساسة عبر نماذج عامة.
- لا توجد صفحة مستقلة باسم «الفريق الطبي». نعرض في الرئيسية قسمًا واضحًا: **«استقبال حالات الولادة على مدار 24 ساعة — تحت إشراف كادر طبي متخصص»**. لا نفترض توافر جميع الخدمات أو طوارئ عامة 24 ساعة. نوضح الدوام الاعتيادي منفصلًا. راجع [البيانات الرسمية](CLINIC_MASTER.md) لنطاق الخدمة ووسيلة الاتصال.

## 2. الهيكل المعلوماتي
- صفحات أساسية: الرئيسية، عن الدكتورة، الخدمات، المختبر والتشخيص (حسب الخدمات المؤكدة)، المقالات والتوعية، تواصل معنا، 404.
- صفحات تفصيلية للخدمات المؤكدة والمفيدة للبحث، دون صفحات فارغة أو تكرار. «الكادر المتخصص» يظهر كوصف خدمة الولادة لا كسيرة لأشخاص مجهولين.
- ترتيب الصفحة الرئيسية: Hero واضح + تواصل، تعريف موجز بالدكتورة، بطاقات الخدمات، قسم استقبال الولادة 24 ساعة، المختبر/التشخيص بحسب التوفر، إرشادات توعوية، معلومات الزيارة والخريطة والدوام، Footer.
- على الهاتف: Header مختصر وشعار صحيح وقائمة واضحة، CTA رئيسي قابل للمس، ظهور محتوى أساسي دون سحب أفقي، وعدم تغطية المحتوى بأزرار عائمة.

## 3. الهوية البصرية وفن التصميم
**المصدر الملزم الوحيد للألوان والشعار والخطوط:** [VISUAL_IDENTITY](../brand/guidelines/VISUAL_IDENTITY.md)، ولا تعاد صياغة رموز الشعار أو تلوينه خارج نسخ أصوله الرسمية.
- لوحة الموقع الرقمية: بترولي `#0C495C` رئيسي، فيروزي `#45A18E` مساند، وردي طبي `#C76D8C` مساعد محدود، خلفية `#F4F8F7` مع أبيض ودرجات نص مناسبة.
- الوردي للزخارف الرقيقة، أشرطة صغيرة أو خلفيات بتعتيم خفيف، لا للسطوح المهيمنة أو النصوص منخفضة التباين. البترولي للأقسام الأساسية والعناوين وCTA حسب التباين.
- الخط الرقمي IBM Plex Sans Arabic عند توفر نسخة ذات ترخيص صحيح؛ لا ننشر ملفات الخطوط التجارية المرفقة بالهوية قبل التحقق من الترخيص.
- تصميم أصيل، طابع طبي راقٍ، منحنيات هندسية مشتقة بحذر من الرمز، مساحات بيضاء وتدرج بصري واضح: عنوان ← رسالة ← CTA.
- تباعد وسلّم Typography وRadius وظلال وأيقونات موحدة عبر Design Tokens ومكونات مشتركة؛ لا تغييرات بصرية عشوائية بين الصفحات.
- الصور حقيقية ومرخصة وملائمة وغير مضللة، دون تصوير مرضى أو شهادات دون موافقة؛ لا صور توحي بإجراءات أو مرافق غير مثبتة.
- تصمم حالات التفاعل: hover/focus/active/disabled/loading/error/success/empty، مع عناوين ورسائل عربية واضحة.

## 4. Mobile-first & responsive
- CSS يبدأ بأصغر شاشة مدعومة 320px؛ راجع 360/375/390/430/768/1024/1280/1440px، والاتجاهين portrait/landscape عند الحاجة. نقاط الانكسار مبنية على انكسار المحتوى لا على أسماء الأجهزة.
- محتوى العمود الواحد على الهاتف، ثم grids مرنة، وضبط طول العنوان والنص والوسائط بحيث لا تتضخم صورة Hero على الديسكتوب ولا تتقاطع مع العنوان.
- أزرار وتحكمات واضحة ومريحة للمس؛ الهدف التصميمي 44×44 CSS px كلما أمكن، مع مراعاة استثناءات WCAG الرسمية، وspacing يمنع الضغط الخاطئ.
- لا Hover-only ولا قوائم مسدلة غير قابلة للاستخدام بلوحة المفاتيح. دعم RTL بالكامل والأرقام وقراءة الجمل المختلطة.
- Header لا يبتلع مساحة الهاتف، القائمة تغلق بوضوح وبزر Escape مع استعادة التركيز؛ روابط الاتصال وواتساب تعمل من الهاتف.

## 5. البنية الهندسية
- اعتماد المبدأ الخفيف في UPDATE CARD: توليد صفحات مستقلة قابلة للفهرسة من مكونات وبيانات موحدة وقت البناء. تقنيات التنفيذ تُحسم عند بدء البرمجة، ولا يلزم نسخ نفس stack.
- تقسيم مسؤوليات مقترح: `src/config` للهوية العامة والاتصال، `src/data` للخدمات وبيانات المحتوى، `src/components` للمكونات، `src/pages` للصفحات، `src/templates` للقوالب والـ SEO، `src/styles` للـ tokens والأساس والتجاوب والحركة، `src/client` للتفاعل، `src/assets` للأصول المُحسّنة، و`scripts` للبناء والتحقق.
- مصدر حقائق العيادة التحريري `docs/CLINIC_MASTER.md`، مصدر الهوية `brand/guidelines/VISUAL_IDENTITY.md`، والتطبيق يقرأ بيانات مشتركة واحدة مشتقة منهما؛ لا نسخ مبعثرة للرقم أو الدوام أو العناوين داخل صفحات متعددة.
- لا تكرار HTML للبطاقات والنافبار والتذييل، ولا CSS overrides متراكمة، ولا مكتبات ضخمة لحركة بسيطة، ولا ملفات build ضمن Git ما لم تكن هناك ضرورة موثقة.
- تغييرات جذرية من المصدر، تنظيف الكود غير المستخدم والتحقق من الاعتمادات؛ لا حذف تاريخي يعطل الوظائف. نشر إنتاجي من مسار/فرع واضح بعد التحقق.

## 6. الأداء والحركة
- مؤشرات مستهدفة لدى المستخدمين الحقيقيين عند الشريحة 75%: LCP ≤ 2.5s، INP ≤ 200ms، CLS ≤ 0.1. نختبر على شبكة هاتف بطيئة وأجهزة متوسطة، ولا ندعي تحقيقها قبل القياس.
- صورة Hero محسنة بالأبعاد الصحيحة `srcset/sizes` و`width/height` أو `aspect-ratio`، لا lazy-load للـ LCP، مع تحميل كسول لباقي الصور، وAVIF/WebP وفواصل مناسبة.
- تقليل JS/CSS وتقسيم ما يلزم وتأجيل غير الحرج، تحميل خطوط محلية مرخصة مع `font-display:swap`، تفضيل static pages وcache headers الصحيحة.
- الأنيميشن وظيفي وخفيف: `transform/opacity` بدل تخطيط ثقيل، بلا إطالة أو تعطيل القراءة، واحترام `prefers-reduced-motion`. لا نقلد مقدمة شعار UPDATE CARD إلزاميًا؛ نقرر وجودها وشروط ظهورها فقط إن أفادت الزائرة.
- تجنب أي splash أو loading يمنع التواصل السريع؛ حالات تحميل قصيرة وواضحة.

## 7. الوصول والـ SEO والثقة الطبية
- استهداف WCAG 2.2 AA: HTML دلالي، lang=ar وdir=rtl، ترتيب عناوين صحيح، skip link، تركيز مرئي، labels ورسائل الأخطاء، دعم لوحة المفاتيح، تباين نص عادي ≥4.5:1 والكبير ≥3:1، وضبط العناصر غير النصية حسب المعيار.
- SEO: title/description/canonical مخصص لكل صفحة، Open Graph، sitemap.xml وrobots.txt، Breadcrumbs عند الحاجة، Structured Data من النوع الأنسب (مثل MedicalClinic/Physician) بالحقائق الموثقة فقط.
- محتوى طبي محايد ودقيق ومراجَع، لا وعود علاج أو نسب نجاح غير موثقة، ولا ادعاء شهادات أو أجهزة أو خدمات بدون تحقق. تمييز الدوام الاعتيادي عن استقبال الولادة 24 ساعة.
- روابط واتساب/هاتف من المصدر الرسمي، خرائط فعلية بعد توفير/تأكيد الرابط، لا خرائط أو تقييمات أو بيانات معتمدة بالافتراض.
- HTTPS، security headers مناسبة، وعدم تضمين مفاتيح أو بيانات مرضى أو تتبع زائد؛ سياسة خصوصية واضحة إذا استُخدمت أدوات جمع بيانات/تحليلات.

## 8. اختبارات القبول الإلزامية
1. بناء Production، فحص الروابط والصفحات والـ 404، وملفات الصور والخطوط ومراجع البيانات.
2. مراجعة صور/لقطات للهاتف والديسكتوب: Hero، Header/Menu، الخدمات، قسم الولادة، CTA، Footer؛ فحص عدم overflow والتداخل أو صور مشوهة.
3. اختبار على هاتف حقيقي أو محاكي: واتساب، اتصال، تنقل، رجوع، تدوير الشاشة، اتصال بطيء.
4. Lighthouse/PageSpeed وقياسات web-vitals وميزانيات الأصول؛ تسجيل المخالفات وإصلاحها من المصدر.
5. اختبار لوحة المفاتيح وfocus وscreen-reader قدر الإمكان، contrast وreduced-motion.
6. مراجعة طبية تحريرية قبل النشر ومطابقة المعلومات مع المصدر المعتمد؛ إخفاء تفاصيل غير مؤكدة حتى اعتمادها.
7. تحديث الوثيقة نفسها عند تغيير المعيار، دون نسخ `FINAL` أو إصدارات موازية. لا نشر قبل نجاح الفحوص الأساسية.

**قرار الإطلاق:** اعتماد تصميم الصفحة الرئيسية بصريًا على الهاتف والديسكتوب قبل تنفيذ بقية الصفحات؛ ثم إنشاء مكونات التصميم المشتركة وتوسيعها تدريجيًا.
